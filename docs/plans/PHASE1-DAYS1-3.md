## 1. 三天结束时要交付什么

在同一个 develop 提交上启动一个 Go Server 和两个独立 C++ 客户端：

连接 → 开发用登录 → 分配同一房间 → WASD 输入 → 服务端 30Hz 模拟 → 10Hz 快照 → 两端显示双方位置。

同时提供一个能走相同协议的 Go Bot，完成 10 Bot / 5 房间的小规模稳定性检查；Prometheus/Grafana 能展示真实在线人数、房间数和 Tick 耗时。

本阶段展示的是**服务端权威移动原型**。客户端用几何图形区分玩家，位置先由服务端快照驱动；10Hz 显示可能有阶梯感，流畅度优化留给预测与插值阶段。

| 本阶段必须交付 | 留到后续阶段 |
| --- | --- |
| TCP Frame、协议生成、开发用登录、基本 Session 状态校验 | 正式账号注册、密码登录、鉴权体系、完整重连 |
| Room 单写入者、固定 Tick、移动、快照 | 怪物、子弹、碰撞、伤害、关卡、奖励、AI Director |
| C++ 窗口、输入、收发队列、双人位置显示 | 预测、校正、插值、美术、音效、ImGui 完整面板 |
| 有界收发队列、基础慢客户端隔离、断线清理 | 大规模网络优化与完整可靠性策略 |
| 最小 Bot、真实指标、基础联调证据 | 1000/5000 Bot 性能承诺、完整 Vue 管理后台 |
| MySQL/Redis 连通性检查、配置可复现 | 业务表结构、持久化实现、Redis 排队/路由业务 |

MySQL/Redis 的现有容器环境可以使用，但移动链路前三天不依赖数据库读写。匹配先在进程内完成，实时 Tick 不访问数据库。

## 2. D1 开工对齐：先统一这些约定

建议用 45 分钟由 A 主持协议对齐、C 确认跨语言实现、B 确认模拟语义、D 确认匹配与验证方式。

| 对齐事项 | 建议约定 | 最终落实人 |
| --- | --- | --- |
| 最小消息集 | Ping/Pong、LoginRequest/Response、MatchRequest/Found、PlayerInput、WorldSnapshot；具体 ID/字段编号由 A 提案 | A，C 复核，B/D 确认语义 |
| Frame | 16B、大端、Magic=0x4E52、Version=1；首版 Flags/Reserved=0；Body 上限建议 64KiB，分配内存前检查 | A + C |
| 登录 | development 模式下使用测试昵称，服务器分配 Session/Player ID；明确不具备正式身份认证能力 | A |
| 房间 | 演示房间容量 2；为了 D2 联调，允许首名玩家入房后移动，第二名玩家加入同房间；不涉及战斗开局规则 | B + D |
| 坐标与移动 | 服务端二维 x/y 映射客户端 x/z；演示边界 [0,20]×[0,20]，速度 5 单位/秒；方向先校验有限值再限制长度 | B + C |
| 时间 | 服务端 Tick=30Hz，Snapshot=10Hz，客户端 Input=30Hz；客户端帧率不决定服务端位移 | B + C |

| 停止移动 | 按键释放发送零输入；建议最后有效输入超过 200ms 未更新则清零移动意图 | B + C |
| 快照 | 至少有 room_id、server_tick、玩家 ID/位置/速度、自己的 LastProcessedInputSeq；完整快照中缺失的实体要从客户端移除 | B 定义视图，A 定义 DTO，C 消费 |
| 未实现动作 | PlayerInput 可保留瞄准/射击/药水字段；前三天只实现移动，其他动作的忽略/拒绝语义在协议表中写清 | A + B |
| 关闭与清理 | EOF 触发会话清理；建议 2 秒内从房间移除玩家、5 秒内销毁空房间；本阶段重连视为新会话 | A + B + D |
| 队列策略 | Reader/Writer 分开；队列必须有上限；Snapshot 槽位建议 1、旧快照被新快照替换；可靠队列饱和时关闭慢连接并记录原因 | A，B/C/D 配合 |

跨模块交付关系：

| 提供方 → 使用方 | D1 要对齐的契约 | 边界要求 |
| --- | --- | --- |
| A → C/D | proto、消息 ID 表、Frame 十六进制固定样例、错误处理表 | C++/Bot 使用同一协议；不各自增改消息字段 |
| A → B | Join/Leave/Input 等 Domain Command 的投递方式与返回结果 | Network 不直接写 Player/World |
| B → A | 房间结果及不可变快照视图，可靠消息/快照分别投递 | Room 不直接写 Socket，也不把 protobuf 当 Domain Model |

## 7. 每日联调怎么组织

每天最后 90 分钟保留给评审、合并和联调，最后 30 分钟只处理验收阻断问题。

1. 四人先报告本日交付物、接口变更和阻塞；跨人接口问题持续超过 30 分钟就同步，不等到晚上。
2. 功能分支从 develop 开始：A feature/network，B feature/game-core，C feature/client，D feature/platform。
3. A 的 proto/契约增量优先评审；B/D/A 按依赖接入服务端，C/D 接入真实客户端与 Bot。不要等四人所有功能写完才第一次合并。
4. Reviewer 固定为 A↔C、B↔D；协议变更额外由 A 统一审核。gameserver 入口/config 的并发改动由 A 统一组装，D 配合，避免多人同时重写入口。
5. C 选定当日 develop 提交号，四人都使用该提交重新构建、生成协议；D 记录进程、端口、版本和命令。
